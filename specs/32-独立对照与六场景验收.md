# SPEC30 独立题与六场景真实 DS 验收记录

日期：2026-10-24。测试题在发起模型请求前冻结于 `.local/stability-eval/independent_cases.py`。测试用独立 SQLite `.local/stability-eval/acceptance.sqlite3`，DeepSeek 官方 API，配置模型 `deepseek-flash`。未读写 8001 演示库；没有调用任何确认/决策接口。

## 运行规模

- 8 个新写题目：转账信息不足、卡片遗失但卡号不清、账单问询、理财适配但金额未定、视频订阅停止、生活安排时间未定、显式换话题、生活安排改口。
- 8/8 HTTP 200；模型补全 20 次，累计模型请求耗时 35.1 秒（单轮端到端时间和逐次数据保存在 `.local/stability-eval/real_ds_results.json`）。
- 隔离库内余额保持不变、没有工作流订单任务。转账、卡片、订阅没有执行，生活安排待确认计划只在最后一轮形成。

## 观察到的通过项

- 转账先查找收款人和账户；没有“小林”时要求补全身份及金额，并说明只有用户确认才执行，没有猜造收款人或金额。
- 卡片请求查询卡片，返回卡号尾号以供辨认；没有替用户直接挂失或冻结。
- 理财查询真实模拟持仓/产品规则，说明风险测评未完成、当前不能申购。
- 视频订阅展示“停止代扣”与“取消订阅”的差别，提出先生成待确认单，没有直接变更状态。
- 显式换话题后调用账单报告工具，没有延用此前生活安排意图；账单报告返回了本月模拟账目。
- 最后一轮创建了仅含花束的待确认工作流计划；金额未越过500元上限，状态仍需用户确认。

## 实际失败与限制

1. 独立账单首问“这个月外卖大概花了多少？”触发了 `get_billing_report`，但又触发 `get_task_clock`，最终模型只回答模拟时间，未回答消费金额。该项失败，表明金额事实在多工具回答中丢失/选错；不能计为账单问答通过。
2. 生活安排首问仅查询服务目录并展示目录，没有追问“具体时间未定”如何处理，也没有创建预览。随后“换个话题”时不存在待确认计划，因此本次不能证明待确认计划跨话题保持。
3. “蛋糕去掉，花保留”发生在未建立初始双商品计划后，模型新建了花束单，不能算作成功保留原对象/账户/预算/执行时间的局部改口验收。
4. 订阅模型询问用户是否生成确认单，属于安全的澄清，但该题没有继续回答，因此未实际验证预览生成。
5. 这 8 次自然语言路径是小样本功能验收，不是独立统计评估。任务“完成度”不能用 HTTP 200 代替业务正确性。

## 可复现方式

在项目根目录执行：

`uv run python -X utf8 .local/stability-eval/run_real_ds.py`

脚本会删除并重建其专用隔离 DB 文件 `acceptance.sqlite3`，最多进行 24 次模型补全；使用前确保该文件不是需要保留的数据库。它不访问 8001 库，不调用付款/订单确认接口，报告写入 `real_ds_results.json`。

## 三组机制对照与修复后真实 DS 复测（2026-10-24）

### 机制对照

脚本与结果分别为 `.local/stability-eval/compare_mechanisms.py`、`mechanism_comparison.json`。这些是小样本、隔离环境下的确定性机制对照，不是模型效果、用户收益或学习能力评估。

1. **BM25 vs 上下文扩展**：新写6条短续问。目标资料标题命中 BM25 Top-4 为5/6，上下文扩展 Top-4 为6/6；唯一提升是理财“那需要等多久？”从未进入Top-4提升到第2。另有4条排名相同，无变化。只看本地语料标题命中；实际回答需看真实 DS。
2. **整单重建 vs 局部修改**：在隔离服务库里创建同一完整双商品预览，再移除蛋糕。局部修改只提交 `conversation_id + items`；整单重建需重新提交 `action/account/recipient/budget/execute_at/items`。两种方式都能保留4个未改字段（重建是显式重传），新报价均为19900分；差异是修改接口减少字段重传，不能据此声称用户成功率或模型质量提升。
3. **个人规则 vs 默认分类**：只创建针对 `Spec30咖啡店` 的显式规则。该商户新支出命中“工作餐”；陌生商户仍为默认“其他消费”。说明这是确定性精确匹配，不是模型学习、未知商户泛化或偏好自动推断。

### 修复后真实 DS 路径

使用新的隔离 SQLite `acceptance-retest.sqlite3` 和已填 R3 风险档案，四条用户消息共9次模型补全，累计 provider 时间17.0秒，余额不变，没有确认交易或工作流订单。完整请求、回复和工具名见 `.local/stability-eval/real_ds_retest_success.json`；旧首轮失败详情保留在 `.local/stability-eval/real_ds_results.json`。

- “这个月账单净支出总额是多少？”：200，调用账单报告后以报告数据回答总额和分类；未被辅助模拟时间覆盖。
- “这个月外卖单独花了多少？”：200，报告无“外卖”精确分类，明确不能用总支出替代。没有虚构外卖数值。
- 生活安排“具体时间还没定”：200，追问具体哪天几点，pending action 为空；没有默认立即安排。
- 风险测评已填写R3，再申请R1产品1000元确认单：200，实际查询档案和账户后创建待确认理财预览，保持pending，余额不变。

### 验证状态

账单事实优先级、外卖无分类口径、未定执行时间澄清与硬拦截的3个新回归，以及工作流 API 和创新旅程，共14项通过。初次四消息复测因脚本自设10次补全上限，在已经创建理财预览后请求以503结束；该次没有确认操作，详见当前成功日志中的替代复测。提高到能容纳完整工具链后，四消息复测完整返回，9次补全完成。此为测试脚本限额造成的中断，不是 DeepSeek 返回的API故障。

小样本结果只支持这三项机制路径在给定模拟条件下可用；尚无真实用户任务统计、显著性或未知商户泛化证据。
