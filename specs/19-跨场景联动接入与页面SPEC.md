# 跨场景联动：接入与新增页面 SPEC

日期：2026-10-13。状态：用户已批准样稿并授权实施。只新增我的安排业务区，不改现有界面；前端继续medium。按用户要求不增加hash校验、校验和或额外dry-run流程，直接走现有模拟银行／商户的正常下单与失败退款流程。

## 1. 首版范围与复用

先完整实现“预算内为家人安排生日”：理解对象、预算和执行时间 → 查询模拟服务和可用资金 → 选择鲜花／蛋糕 → 汇总报价 → 明确确认 → 预留 → 分步下单 → 核对订单、资金和异常恢复。

复用已有WorkflowService、FundHold、TaskClock、事件版本、会话／确认面板；补齐模型工具、页面和API对话关联。当前代码已有商户目录、报价、下单、取消、退款与恢复，以及相应用例；已有代码不代表模型和用户页面已接通。

首版仅现有模拟鲜花、蛋糕两种服务，每项1–5份；不加入真实商户、配送地址、电话、推荐平台、通用任意任务规划或新框架。它是一条可验证的多业务流程，不能称为已具备通用自主规划。

## 2. 信息架构与不变项

- 保持账户／账单／财富／生活四入口、置顶／最近、侧栏宽度及折叠规则不变。
- 生活保留当前“订阅与周期支出”为默认页，只新增“我的安排”二级页，scope=`life/arrangements`；本轮不单开商城、服务订单、日历或新一级入口。完整地图的其他页面后续再建设。
- 我的安排采用列表 → 同页详情／创建的结构；目录、报价与选品嵌入创建流程，订单嵌入步骤详情。
- 现有正文14.5px、标题16px、灰绿配色、用户气泡、680px聊天阅读列和可调整右面板全部沿用。生成图只评审新增业务区，不覆盖既有设计。
- 主对话可提出生日目标。必要补问后在当前对话准备方案；不强制拆新聊天。页面新建安排时创建独立普通对话；后续取消、核对、继续讨论始终复用该任务原对话。

## 3. 创建与报价

页面最少字段：对象称呼、预算（元）、付款账户、选中服务与数量、立即／指定时间。对象称呼只用于模拟；指定时间明确北京时间。服务价格、版本、可取消条件从目录读取，不能由模型编造。

引用现有目录：花间花坊生日花束199元，云朵烘焙生日蛋糕129元。例：预算500元、各一份，报价328元，未用预算172元。只预留实际报价328元，不预留500元；报价不足预算不表示已经省下或到账。

前端可显示试算，但预览接口返回的金额和条件才用于确认。报价有效10分钟；预算、对象、服务数量、时间或付款账户修改必须重新预览，旧确认失效。只读提问不作废方案。

点击“核对方案”打开既有右侧确认槽：逐项名称／数量／价格、总额、预算、账户、执行时间、24小时执行窗口、将预留金额和异常补偿范围。右侧对话和确认不并排叠加；可返回原对话或关闭，关闭不等于取消。

确认文案须说明：确认后按原报价预留；成功指模拟订单被接受，不代表已配送；某项失败时停止后续下单，释放未消费预留，并在本次明确授权范围内取消／退款已成功且可取消的订单。

## 4. 安排列表与详情

列表只展示已确认的持久任务，默认最近更新优先；已有接口若无更新时间，首版按返回顺序，不靠模型推断。待确认草稿留在原对话／当前编辑页，不伪造为已安排记录。列表至少给标题、对象、执行时间、状态和报价；状态筛选复用同页，不新增菜单。

详情展示：

1. 标题、状态、对象和执行时间。
2. 开放式金额摘要：预算、报价、当前预留、已支付、已退款、待退款和实际净支出。净支出=已支付−已退款，待退款未入账之前不能提前抵减。
3. 按执行顺序展示服务步骤、商户订单、金额和结果；订单编号及细节折叠。
4. “继续对话”；可取消时“取消安排”；结果待核对或待退款时“核对处理进度”。操作使用原任务ID，不重新下单。

确认受理、等待执行、正在执行、订单已确认、退款处理中是不同状态。前端使用结构化状态和state_version，页面轮询不调用模型，不允许晚到事件回退回执。

## 5. 状态与金额示例

| 场景 | 页面状态与关键金额 | 可做什么 |
|---|---|---|
| 待确认 | 报价328、预算500；尚未预留或支付 | 修改方案、确认、取消预览 |
| 指定未来执行且已确认 | 已安排，预留328，支付0 | 继续对话、预览取消 |
| 正常下单完成 | 两订单已确认；支付328、预留0、待退款0 | 查每笔订单；不称已送达 |
| 蛋糕缺货、花束退款处理中 | 花束已付199；蛋糕未扣129；已释放预留129；已退0、待退199、当前预留0、净支出199 | 核对原订单／补偿进度，不报全部完成 |
| 后续退款实际到账 | 已退199、待退0、净支出0 | 查看失败／取消原因及回执；不改写失败成生日任务成功 |
| 回执丢失 | 结果待核对，金额以已记账事实为准 | 查询原订单，禁止重下单或重复支付 |
| 执行超窗 | 安排过期、释放未消费预留 | 原任务终止；如需重新安排另行预览确认 |

无法取消的已履约订单保留实际支出，显示部分处理完成及原因；不能承诺所有取消都能退款。首次确认未授权的新消费或更高报价必须重新确认，不能在恢复时静默扩大预算。

## 6. 模型、API与事件接入契约

沿用[P3-B接口](contracts/fourth-batch-api.md)与现有workflow_router：GET /api/workflows，POST /api/workflows/preview，POST /api/workflow-plans/{id}/decision，POST /api/workflows/{id}/recover。

模型拟增加只读工具“查服务／查安排”和“准备安排／取消预览”；时钟查询复用已接入TaskClock。模型不具备确认、直接支付、模拟商户故障注入、推进时间或追加未授权订单能力。用户要求“帮我给家人过生日”时缺预算、日期等需必要补问。

实施前核对以下增量，不能默认已完成：

- ConversationStore支持life/arrangements，workflow动作关联对应范围；TaskConfirmation与Action类型支持WorkflowAction，确认路由不混到普通转账。
- 当前API有任务集合，详情可从集合选取，不先增加一套重复查询后端。必要时再加精确详情接口。
- 取消／恢复动作回到原conversation_id；任务事件同时关联原创建与取消计划，保留最新state_version。
- 主通知与原对话结果使用同一事件事实；恢复成功后更新原回执，不额外创建“退款对话”。
- GET查询不额外执行新订单；后台负责已授权步骤，recover仅核对已有订单／执行已授权补偿。
- 现有定时与workflow共用演示时钟。沿用当前定时页面的明确演示入口，不在新页面复制另一个时间推进按钮；提示其影响全部已确认且到期安排。
- `enable_workflow_actions`独立开启；工厂默认关闭，主入口在正常下单与失败退款实际验收通过后已开启，见[实施状态](20-跨场景联动实施状态.md)。

## 7. 一张样稿的四个状态

A：方案与右侧确认，500元预算、报价328元。B：未来执行的已安排详情，当前预留328、尚未扣款。C：正常分支，两笔订单已确认，支付328。D：异常分支，蛋糕缺货，花束199元退款处理中。C与D是两种结果分支，不表示同一任务先成功又自动失败。

四格复用同一“生活／我的安排”，现有订阅页不动。图片采用少量准确文案，不放订单长ID，不编预计退款天数；日期尽量只展示必要的北京时间，完整窗口由真实契约计算。列表／创建／详情的返回路径写在SPEC，图中重点画新增的方案和执行状态。

## 8. 验收与后续实施次序

1. 用户审本轮样稿；认可后才分配前端，继续medium。已有服务优先复用，不同时重做视觉系统和规划框架。
2. 先做API／模型工具／事件对话契约，再接我的安排页面；正常路径先通过，接着验证异常分支。
3. 用例包括：预算不足与无效金额；预览不扣款、确认只预留报价；定时不提前执行；取消释放预留；重复确认／worker／重启不重扣；报价变更不超预算执行；回执丢失查询原单；一商户失败后的取消退款；退款暂失败后恢复；不可取消订单保留真实支出；范围与对话归属；窄屏右面板和原界面回归。
4. 先确定性测试，再用少量真实DS调用和独立演示库做浏览器完整路径。故障模式只在隔离验收实例启用，正常用户页不增加故障开关。
5. 成功后再开放workflow，并做六场景总体验收；创新对照与比赛材料随后推进，不把当前工程组合当作未经实验的创新结论。
