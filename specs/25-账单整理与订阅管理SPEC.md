# 账单整理与订阅管理 SPEC

日期：2026-10-22。用户已认可四格样稿并授权接入前端，继续medium，重点完成真实用户流程和bug修复，创新暂缓。整体布局、字体、四入口保持。

## 1. 交付范围

- 账单：分类/标签/备注修正；商户/类别/来源检索；手工收支；导入记录更正与移除；按批次撤销本次新增记录。
- 订阅：自建记录、金额/周期/续费日/提醒；编辑与移除；周期候选确认/否认/忽略及恢复；账单依据显示日期、商户、金额，避免只展示内部编号。
- bug：优先修复保存、筛选、刷新恢复、重复提交、统计不一致，以及来源混淆。每个修复有重现或针对性检查，不为凑数量重构。
- AA非均摊、预算设置、模板、通知汇总等仍按后续路线图。本轮不做创新实验、hash检验、dry-run、大型证据包或公网发布。

## 2. 账单数据与操作

银行流水的金额、日期、收支类型和原始描述保持只读；可独立补充分类、最多10个标签、备注。用户修正保存在独立元数据中，重启seed和重新识别不得覆盖。明确区分原始来源与用户修改值。

导入/手工记录允许更正日期、商户、金额、类型、分类、标签和备注；人民币整数分，最多两位小数，收入/退款为正、消费为负，表单输入正数由类型确定方向。手工记录不改变银行余额；不允许伪装银行来源。演示样例仅开放分类/标签/备注修正。

列表和分析必须用同一份有效记录；分类修改后统计同步。筛选覆盖开始/结束日期、商户或备注关键词、类别、来源；清除筛选回到全部，不用改路由结构。返回原列表保持筛选与滚动位置。

导入返回batch_id、文件名、时间、新增/重复/错误数。批次只拥有本次实际新增记录，重复项不归本批次；撤销不删除此前批次、银行或手工记录。重复撤销不重复操作。已撤销批次以后可重新导入，仍按现有去重规则处理。历史旧导入没有可靠批次时标“历史导入”，可逐条更正/移除，不猜测文件归属。

保存使用版本防止覆盖别人刚保存的修改；新建和导入重试用请求标识避免多记一笔。同内容但真实独立的手工支出允许存在，不能机械按相同金额商户合并。移除记录/批次会更新分析与订阅候选；历史聊天中原答复保留时点含义，不改写过去对话。

## 3. 自建订阅与候选

个人记录字段：名称、金额、周期（周/月/季/年）、下一续费日、分类、备注、提醒开关及提前天数（0–30），稳定id和版本。显示“个人记录”，只能管理记录、提醒或标记已结束；不能调用商户取消/银行停代扣接口。已有三个模拟合同及取消/停代扣流程保留，并与个人记录清楚区分。

候选反馈取值：确认订阅、不是订阅、忽略、恢复默认。反馈绑定稳定商户与周期身份，不因新增账单导致候选ID变化就丢失；确认不会自动造可操作商户合同。点击“确认并记录”时带入识别金额、周期、预测日期，用户核对保存后创建个人记录并关联候选，重复点击不造重复订阅。

识别依据返回实际条目（id、日期、商户、金额、来源），按日期显示。被移除的条目不继续作为当前候选依据；用户反馈仍保留以便该商户再次出现时继续生效。忽略项可从“已忽略”筛选恢复，不抹掉原始账单。

提醒只写应用内主对话/通知，不发外部消息，不自动扣款。每条记录每次续费日期只提醒一次；关闭提醒或结束/移除记录不再产生新提醒。修改日期后以新日期为准。历史已发通知保留发出时事实。暂停应用不发通知，重启后核对当前日期；过期记录提示待更新，不偷偷推算下一次续费。

## 4. 新增交互样稿

复用现有单右面板，不增加一级/二级页：

A 收支明细的“整理”入口→右侧编辑分类、标签、备注，银行金额只读。
B 导入整理的“导入记录”→批次详情与撤销确认，清楚显示只影响本批次新增。
C 订阅页的“添加订阅记录”→右侧个人记录表单，金额/周期/日期/提醒，保存后回列表。
D 周期候选→真实账单依据，以及确认并记录/不是订阅/忽略；个人记录与已接入合同分区保持现有开放列表风格。

一张四格评审板，不重新生成整套风格。手工记账复用A的编辑表单，通过“手工记账”进入时解锁记录字段；删除、放弃未保存、冲突提示复用已有管理面板样式。

## 5. 模块与API约定

BillingService统一投影银行/导入/演示/手工记录及元数据，避免前端仅改显示而统计用旧值。SubscriptionService统一返回合同、个人记录、带反馈的候选和真实依据，模型查询同一份结果。

拟定HTTP：GET /api/billing/entries 与 report 扩展query/category/source；POST /api/billing/manual；PATCH/DELETE /api/billing/entries/{id}；GET /api/billing/import-batches；POST /api/billing/import-batches/{id}/undo。原导入接口兼容增加client_request_id。

GET /api/subscriptions兼容原subscriptions/candidates并增personal_records；POST /api/subscription-records；PATCH/DELETE /api/subscription-records/{id}；PUT /api/subscription-candidates/{id}/feedback。写入依据当前version，返回保存后的条目；候选确认建记录需entries由服务端重新计算，不能信前端传金额为合同。
