# 接口与状态契约

接口以服务端契约为准。模型产生的数据只能提出操作，可信身份、规则版本、确认摘要和执行回执由服务端填写。

## 通用对象

| 对象 | 必需字段与约束 | 来源 |
|---|---|---|
| RequestContext | request_id、session_id、actor_id、认证强度、时区、trace_id | 可信应用入口；模型无权覆盖 |
| Money | currency 固定 CNY；amount_minor 为整数分；正负语义由字段定义 | 输入规范化后再进行业务校验 |
| ActionPlan | plan_id、版本、动作、规范化参数、步骤依赖、预算、失效时间、policy_version、plan_hash | 模型提出候选，服务端规范化与绑定 |
| ApprovalRecord | approval_id、actor_id、plan_id、plan_hash、权限范围、签发与过期时间、单次使用标识、决定 | 已认证用户的独立确认入口 |
| ToolResult | operation_id、状态、错误码、事实字段、证据 ID、业务状态版本 | 业务执行或查询服务 |
| TaskTrace | task_id、节点状态、plan_id、operation_id、关联事件与时间 | 运行时和业务审计联合生成 |

ActionPlan 的每种动作使用明确的参数 schema，不能用无类型的任意对象直接执行。定义完整 OpenAPI 前先固定领域对象，再生成模型工具 schema 和前端类型；不得分别手写互不一致的三份 schema。

即时内部转账的机器可读草案为 [transfer-plan.schema.json](contracts/transfer-plan.schema.json)，合成示例为 [transfer-plan.example.json](contracts/transfer-plan.example.json)。这是已规范化的服务端计划；模型候选只能提交其允许填写的字段。schema 的 readOnly 标注不提供安全保护，服务端必须拒绝模型覆盖身份、版本和摘要。

## 经济参数绑定

确认绑定动作类型、出入账户、已消歧收款人、金额、币种、费用、执行时间、产品或商户、预算上限和规则版本。规范化 payload 禁止浮点金额，使用固定字段与排序、UTF-8 编码计算 SHA-256；算法和测试向量在实现时固定。摘要由服务端生成，不采信模型或客户端提交的摘要。

预览、确认和提交都引用相同计划版本。字段变化、授权主体变化、规则版本变化或相关状态版本失配时，计划失效，重新预览并确认。执行时再次检查余额、归属与账户状态。

单动作计划的确认在账务提交时原子消费。首版复合计划使用服务端计划和确认记录限定步骤，提交时核对当前步骤参数；不引入额外签名授权服务。步骤分别幂等、共享总预算约束；不得把父计划确认作为任意新工具调用的通行证。增加步骤或改变经济参数后重新确认，已完成步骤不会在恢复时重复执行。

## 接口目录草案

| 接口 | 用途 | 关键约束 |
|---|---|---|
| POST /v1/tasks | 接收任务消息 | 绑定服务端身份及请求 ID |
| GET /v1/tasks/{task_id} | 查询进度与回执 | 会话与用户归属检查 |
| POST /v1/tasks/{task_id}/messages | 补充信息或修改需求 | 修改经济参数后旧计划失效 |
| GET /v1/plans/{plan_id} | 操作预览 | 返回确切参数、费用、风险与失效时间 |
| POST /v1/plans/{plan_id}/decisions | 确认或拒绝 | 身份绑定；模型工具中不提供确认接口 |
| POST /v1/operations | 受控提交 | 仅执行服务调用；有效确认、幂等及事务检查 |
| GET /v1/operations/{operation_id} | 查询实际执行结果 | 确定完成、失败或待对账，不能重新触发执行 |
| GET /v1/accounts/{account_id}/transactions | 查询流水 | 归属、分页、日期与金额语义固定 |

操作提交可以作为内部服务接口，不要求暴露公网 HTTP。接口目录是设计契约，不是官方指定评测协议。

## 状态迁移

任务状态：`RECEIVED → CLARIFYING / PLANNING → AWAITING_APPROVAL → EXECUTING → VERIFYING → COMPLETED`。允许分支为 `REJECTED`、`CANCELLED`、`EXPIRED`、`FAILED`、`PARTIAL`、`UNKNOWN_PENDING_RECONCILIATION`。

计划状态：`DRAFT → VALIDATED → AWAITING_APPROVAL → APPROVED → CONSUMED`；失效分支为 `INVALIDATED`、`DECLINED`、`EXPIRED`。审批记录使用、幂等记录和本地账务提交在同一事务中关联。

响应超时不代表业务未执行。进入 `UNKNOWN_PENDING_RECONCILIATION` 后先按 operation_id 查询，再决定是否恢复；不能盲目生成新幂等键重复扣款。

## 错误语义

`NEEDS_CLARIFICATION`、`SCHEMA_INVALID`、`UNAUTHENTICATED`、`FORBIDDEN`、`APPROVAL_REQUIRED`、`APPROVAL_EXPIRED`、`PLAN_CHANGED`、`STATE_CHANGED`、`INSUFFICIENT_FUNDS`、`LIMIT_EXCEEDED`、`IDEMPOTENCY_CONFLICT`、`PROVIDER_TIMEOUT`、`PROVIDER_RATE_LIMITED`、`BUDGET_EXCEEDED`、`TOOL_FAILED`、`RECONCILIATION_REQUIRED`。

所有错误带用户可理解的说明、是否可重试及下一步动作。同键不同参数为冲突；同键同参数返回原结果。同一个失败不得同时被计为成功和补偿完成。
