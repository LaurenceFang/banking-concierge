# 可用性验收与轻量评测

主线验收检查用户能否完整办成事情、是否少走步骤、失败后能否继续。官方评分维度保留在项目范围中，内部不自行换算总分。

## 每个场景的最小验收

1. 正常请求从对话到实际业务结果完整跑通。
2. 缺少信息时只追问必要项，已知信息不重复收集。
3. 用户改口、取消或工具失败后有明确可继续的路径。
4. 页面能看懂预览、处理中、完成和失败状态。
5. 金额、账户归属、确认和重复执行的必要约束成立。

先为六场景各建立一条主路径和少量重要异常案例。关键业务变化做针对检查，不要求每次改动都重跑大型攻击与研究基准。

## 知识库验收

六场景各至少两条常见问题，检查检索结果、回答是否有用、能否继续办理。真实余额、持仓和交易状态从业务工具取得。没有相关知识时给出明确下一步。

## 优先指标

完整任务完成率、对话轮次、无效追问、首响应和总体等待时间、改口及失败恢复、知识回答相关性。只保存版本、结果、关键失败与 token 用量，不制作逐轮证据包。

## 必要业务与安全检查

保留重复扣款、越权、缺确认、余额不足与注入数据的少量代表用例。安全自评复用这些实现和已知问题，不把所有正常业务塞进人工审批流。

## 创新实验

现成基线和改进版本保持可切换。待可用流程稳定后，针对中文追问规划或不规则订阅识别做小规模同任务对照，再决定是否扩大实验。未执行的结果不填成绩。

## 真实 API 的边界

模型最小连通测试仅确认指定 API、JSON 和工具调用能力，不代表完整银行场景已经实现。模型用量和错误记录用于实际运行维护。
